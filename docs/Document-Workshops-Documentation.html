Document Workshops · Project documentation

A block editor that saves itself and keeps your pages private

Document Workshops is a web workspace for writing. You type / to drop in headings, tables, Kanban boards, callouts and code snippets; every change is saved to the cloud a moment after you stop typing; and an optional encrypted vault locks your documents so even the database can't read them. This page explains how it is built, how a request travels through it, and how to run and deploy it.

React 19 Vite Redux Toolkit Tailwind Express 5 MongoDB Atlas JWT AES-256-GCM
01
What it is
A document workspace that sits between a database and a word processor

Most notes tools are either structured (a database with rows and columns) or flexible (a blank page). Document Workshops joins the two: a page is a flexible, Google-Docs-style canvas, but every page is stored as an ordered list of typed blocks in MongoDB, so a paragraph, a table and a task board can live side by side and still be validated, saved and searched like data.

AreaWhat you get
WritingBlock editor with a / command menu, formatting toolbar, undo and redo, find and replace, outline, ruler, word count and page breaks.
Rich blocksEditable tables, Kanban boards (columns and cards), to-do lists, callout notes, quotes, dividers and code snippets.
SavingDebounced auto-save to MongoDB Atlas, with revision checks so two tabs can't silently overwrite each other.
AccountsEmail and password, or Google sign-in. Each user only ever sees their own documents.
PrivacyAn optional end-to-end encrypted vault: titles, icons and content are locked in the browser before they are sent.
ExportDownload any document as a Word (.docx) file, or print it.
Try before signing upGuest mode opens a starter document that works fully in the browser without saving to the server.
ℹ️

What "collaborative" means here. Your account can be open on several tabs and devices at once, and the app protects each page with a revision number so edits never overwrite each other unnoticed. It is not a live co-editing tool with shared cursors; that would need a websocket layer, and this version uses plain HTTPS requests only.

02
Architecture
Three boxes, one direction: browser, API, database

The frontend is a static site. Vercel serves it once, then the browser runs everything. Whenever it needs data it calls the Express API on Render, and only the API ever talks to MongoDB Atlas. The database is never reachable from the browser.

1 · Browser (React app from Vercel)
Renders the editor, keeps the open document in Redux, encrypts and decrypts if the vault is on, and adds an Authorization: Bearer token to each API call.
2 · Express API (Render)
Runs the request through a chain of checks (see section 09), then a controller reads or writes MongoDB. Every query includes the signed-in user's id.
3 · MongoDB Atlas
Stores users (with hashed passwords and hashed session tokens) and documents (a list of blocks, or locked ciphertext if the vault is on).

Every page is a list of small, typed objects

A document's content is an array. Each entry has an id, a type and the fields that type needs. The server only accepts fifteen known types, and it checks the shape of each one before saving, so a broken or hostile block can't end up in the database.

Auto-save
Edits reach MongoDB a moment after you stop typing

Saving on every keystroke would send hundreds of requests a minute. Instead the editor debounces: each change restarts a 600 ms timer, and only when you pause does one request go out carrying everything that changed. Try typing in the box below and watch the counters.

Start typing. Many keystrokes become very few requests.

What happens on each save

1 · Collect changes
Title, icon and blocks that changed are merged into one pending update. Switching to another document throws away the old timer, so a save never lands on the wrong page.
2 · Send with the revision
PUT /api/documents/:id with the revision number you last saw (in an If-Match header or the body). No revision means 428 Precondition Required.
3 · Server compares
If the stored revision still matches, the update is applied and the revision goes up by one. If not, someone else saved first and the server answers 409 Conflict.
4 · Handle a conflict kindly
The browser fetches the server copy. If it is identical to yours, or unchanged from what you started with, it quietly adopts the new revision (or retries once) and you see nothing. Only a real difference shows the conflict banner so you can choose.
The debounce idea (simplified from useAutoSave.js)
// Every edit calls queueAutoSave(). Only the last one in a quiet period sends.
function queueAutoSave(updates) {
  pending = { ...pending, ...updates };      // merge title / icon / content
  setSaveStatus('saving');
  clearTimeout(timer);                       // restart the countdown
  timer = setTimeout(() => flush(), 600);    // 600 ms of silence
}

async function flush() {
  try {
    const saved = await documentServices.update(docId, pending, {
      expectedRevision: activeDoc.revision   // sent as If-Match
    });
    setSaveStatus('saved');
  } catch (err) {
    if (err.status === 409) tryQuietRebaseThenShowConflict();
    else setSaveStatus('error');
  }
}
// Ctrl+S calls flush() immediately instead of waiting.
StatusMeaning
savedThe server has your latest edit.
savingA request is queued or in flight.
conflictThe page changed elsewhere and the two versions really differ. Nothing is overwritten until you decide.
errorThe request failed (for example offline). Your text is still on screen.
guestGuest mode: kept in the browser only.

{

08

        

          
Accounts and sessions

          
Short-lived tokens, a long-lived cookie, and no passwords stored

        

      


      
Signing in produces two things. An access token (a JWT valid for 10 minutes) goes in the Authorization header of every API call. A refresh token (valid 7 days) lives in an HttpOnly cookie that JavaScript can't read, so a script injected into the page can't steal it. When the access token expires, the app swaps the cookie for a new one in the background and replays the failed request, and the user never notices.


      

        

          

          
1 · Register or sign in
Email and password (8 to 128 characters with an upper-case letter, a lower-case letter and a digit), or "Continue with Google". Passwords are hashed with bcrypt (12 rounds); the plain password is never stored.

        

        

          

          
2 · Server issues two tokens
Access JWT in the response body. Refresh token in a Secure, HttpOnly cookie. The database keeps only a SHA-256 hash of the refresh token, one entry per device (up to 10).

        

        

          

          
3 · Normal use
Each request carries the access token. The auth middleware checks the signature and expiry, then puts the user's id on the request. Routes never trust an id sent in the body.

        

        

          

          
4 · Silent refresh
A 401 TOKEN_EXPIRED triggers one refresh call. Requests that fail at the same moment wait in a queue and are replayed together after the single refresh finishes.

        

        

          

          
5 · Rotation and theft detection
Every refresh issues a brand-new refresh token and retires the old one. A 10-second grace window forgives two tabs refreshing at once; an old token used after that means someone copied it, so that session is revoked.

        

      


      

        

          
DetailWhy it exists

          
            
Google sign-inThe ID token from Google is verified on the server (signature, that it was issued for this app's client id, and that the email is verified). The browser's word alone is never trusted.

            
Verification emailA one-time link is emailed after registration. Only its hash is stored in the database.

            
Two different secretsAccess and refresh tokens are signed with different secrets, each at least 32 characters. The server refuses to start otherwise.

            
Access token in memory-like storageShort life (10 minutes) limits the damage of a stolen copy. The long-lived part is the HttpOnly cookie.

            
Rate limitsSign-in, register, Google and verify routes allow 10 tries per 15 minutes per client; background refresh calls allow 60.

          
        

      


      

        
Silent refresh in the API client (simplified from api.js)

        
async function request(path, options) {
  let res = await fetch(API + path, withAuth(options));

  if (res.status === 401) {
    const body = await res.json();
    if (body.code === 'TOKEN_EXPIRED') {
      await refreshOnce();                       // one shared refresh call
      res = await fetch(API + path, withAuth(options));   // replay quietly
    } else {
      signOutEverywhere();                       // revoked or tampered token
    }
  }
  return res;
}

      


    


    
    

      

        
09

        

          
Every request is checked

          
A chain of small guards, each stopping one kind of trouble

        

      


      
A request doesn't reach your code until it has passed a fixed sequence of checks. The order is set in app.js, and each check is small enough to read in one sitting.


      

        

          

          
1 · Helmet and CORS
Safe response headers, and a strict allow-list of frontend origins. No wildcards.

        

        

          

          
2 · Origin guard
The Origin (or Referer) must be on the allow-list, otherwise 403. This is what stops another website from driving your API with a visitor's cookie.

        

        

          

          
3 · Body size limits
512 KB for most routes, 10 MB only for documents. Bigger bodies are refused before they are parsed.

        

        

          

          
4 · Mongo sanitiser
Any key starting with $ or containing . is rejected with 400, so a request like {"email": {"$gt": ""}} can't turn a login check into "match anyone".

        

        

          

          
5 · Rate limiter
10 per 15 minutes on sign-in routes, 60 on background auth calls, 200 on documents and vault. Over the limit gets 429.

        

        

          

          
6 · Access token check
Missing token, expired token and tampered token each get a distinct code, so the app knows whether to refresh or sign out.

        

        

          

          
7 · Validators
Field-by-field rules for every body, and a block validator for documents. Anything unexpected is a 400 with a safe message.

        

        

          

          
8 · Owner filter in the query
Controllers query with { _id, userId }. Someone else's document id simply isn't found, so it answers 404 and doesn't confirm that the page exists.

10

        

          
The encrypted vault

          
Pages locked in the browser, so the database only ever holds ciphertext

        

      


      
Turning on the vault is optional. The user picks a vault passphrase (at least 12 characters, scored for strength). From then on, a page's title, icon and content are encrypted in the browser with AES-256-GCM before they are sent. The server and MongoDB store unreadable envelopes and never receive the passphrase or any key that could open them.

The key chain

      

        

          

          
Passphrase → KEK
The passphrase is stretched with Argon2id (64 MiB memory, 3 passes, a random 16-byte salt) into a Key Encryption Key. A slow, memory-heavy function makes guessing passphrases expensive. PBKDF2 is the fallback if WebAssembly isn't available.

        

        

          

          
KEK wraps the Master Key
A random 256-bit Master Key is created once. Only its wrapped (encrypted) copy is stored. A second copy is wrapped by the recovery key.

        

        

          

          
Master Key wraps each page's key
Every page has its own random key (DEK), stored wrapped next to the page. Changing the passphrase only re-wraps one Master Key; no page needs re-encrypting.

        

        

          

          
Page key encrypts each field
AES-256-GCM with a fresh random 96-bit IV for every field, and the document id and field name bound in as extra authenticated data. A ciphertext copied into another page or field fails to decrypt.

        

      


      

        
Locking one field (simplified WebCrypto)

        
async function encryptField(dek, docId, field, plaintext) {
  const iv  = crypto.getRandomValues(new Uint8Array(12));   // new every time
  const aad = new TextEncoder().encode(`${docId}\0${field}\0v1`);
  const ct  = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv, additionalData: aad },
    dek,
    new TextEncoder().encode(plaintext)
  );
  return { v: 1, iv: toBase64(iv), ct: toBase64(ct) };      // this goes to the server
}

      


      
Living with a vault

      

        

          
MomentWhat happens

          
            
Setting it upChoose a passphrase, receive a 64-character recovery key, and prove you saved it by re-typing two of its groups. Only then is the vault created, and the server also asks for your account password (or a fresh Google sign-in).

            
LockingAutomatic after 15 minutes of inactivity, and on logout or a revoked session. Keys and decrypted text are wiped from memory.

            
Forgot the passphraseEnter the recovery key, choose a new passphrase and get a new recovery key. The old recovery key stops working.

            
Older plain pagesOpen read-only with a "Convert to encrypted" button. "Convert all" downloads a backup first and checks every page by decrypting it again before it counts as done.

            
Plain writes are refusedOnce a vault exists, the server rejects any attempt to store a readable title or content, so a bug can't quietly save plaintext.

          
        

      


      

        
⚠️

        
Lose both the passphrase and the recovery key and the pages are gone for good. That's the point of zero knowledge: the server keeps no spare key, so it can't help and can't be forced to.

Honest limits

          
What the design does not promise

        

      


      
No system is perfectly safe, and a good document says where its edges are. These are the ones to know about.


      

        

          
LimitWhat it means

          
            
A hacked frontendBrowser-side encryption trusts the code the browser downloads. If someone gains control of the Vercel deployment and ships altered code, it could capture a passphrase. Protect the GitHub, Vercel and Render accounts with two-factor sign-in.

            
Malicious script while unlockedAn injected script or a hostile browser extension running while the vault is open can read what's on screen. A strict Content-Security-Policy reduces the chance, and the 15-minute auto-lock reduces the window.

            
Metadata is visibleThe server still sees who owns which page, when it changed, its size and its revision count. Only titles, icons and content are locked.

            
Old copiesA malicious server could hand back an older ciphertext of a page. Revisions detect this during normal saves, but it isn't a full audit trail.

            
Safari and iOSSafari blocks cookies between different sites (for example vercel.app and onrender.com), so users may be asked to sign in again. For a production launch, put the app and the API on one custom domain, such as app.example.com and api.example.com.

            
Not live co-editingTwo people editing the same page at the same moment see a conflict prompt, not each other's cursors.

            
No independent auditThe design was tested during development, but it hasn't been reviewed by an outside security firm.

            
BackupsThe free Atlas tier has no automatic backups. Export your data on a schedule you trust.
